Every release publishes a Docker image to `ghcr.io/kmworks/kmrs` (tags: `latest`, `MAJOR.x`, `x.y.z`; platforms: `linux/amd64`, `linux/arm64`) and prebuilt binaries for Linux (x86_64, aarch64), macOS (Apple silicon, Intel), and Windows (x86_64). The [official Komga Docker instructions](https://komga.org/docs/installation/docker) apply verbatim; just swap the image name.

Want to look around first? The [demo](https://demo.kmworks.date) runs the latest image; find the shared sign-in account on the [Introduction](/server/intro#demo) page.

<Tabs>
  <TabItem label="Docker">

```sh
docker run -d \
  --name=kmrs \
  --user 1000:1000 \
  -p 25600:25600 \
  --mount type=bind,source=/path/to/config,target=/config \
  --mount type=bind,source=/path/to/data,target=/data \
  --restart unless-stopped \
  ghcr.io/kmworks/kmrs
```

An existing Komga `/config` directory (with `database.sqlite` / `tasks.sqlite`) is picked up and upgraded in place.

The kmweb UI is embedded in the binary and served at `/`, so `http://<host>:25600/` works in a browser immediately.

  </TabItem>
  <TabItem label="Docker Compose">

```yaml
services:
  kmrs:
    image: ghcr.io/kmworks/kmrs:latest
    container_name: kmrs
    user: "1000:1000"
    ports:
      - "25600:25600"
    volumes:
      - ./config:/config
      - ./data:/data
    restart: unless-stopped
```

A compose stack can also carry [komf](https://github.com/dyphire/komf-rs) (the metadata fetcher) as a sidecar:

```yaml
services:
  kmrs:
    image: ghcr.io/kmworks/kmrs:latest
    container_name: kmrs
    user: "1000:1000"
    ports:
      - "25600:25600"
    volumes:
      - ./config:/config
      - ./data:/data
    environment:
      # optional: pre-fills the komf integration form in the admin UI
      - KOMGA_KOMF_URL=http://komf:8085
      - KOMGA_KOMF_BASEURL=http://kmrs:25600
    restart: unless-stopped

  komf:
    image: ghcr.io/dyphire/komf-rs:latest
    container_name: komf
    volumes:
      - ./komf-config:/config
    restart: unless-stopped
```

komf's port is deliberately not published: unless you set komf-rs's `KOMF_AUTH_KEY`, its API has no authentication, and only kmrs needs to reach it (see [komf integration](/server/enhancements/komf)). Once the stack is up, open the integrations page in the admin UI (or call `PUT /api/v1/komf/integration` with the same two URLs) and confirm — kmrs mints an API key and provisions komf itself; komf then calls back in Komga mode and starts matching metadata.

  </TabItem>
  <TabItem label="Binary">

Download the archive for your platform from the [latest release](https://github.com/kmworks/kmrs/releases/latest) (Linux x86_64/aarch64, macOS Apple silicon, Windows x86_64).

The binary serves on port 25600 and keeps its configuration and databases in `~/.komga` (override with `--config-dir` or `KOMGA_CONFIG_DIR`):

```sh
./kmrs   # serves on http://localhost:25600
```

:::note
PDF support needs libpdfium at runtime, which the release archives do not include. Download the library for your platform (for example from [pdfium-binaries](https://github.com/bblanchon/pdfium-binaries)) and put it next to the executable, or point `KOMGA_PDFIUM_PATH` at it. Without it, CBZ, CBR, and EPUB still work, but PDF books are reported as unsupported. The Docker image already includes libpdfium.
:::

On Windows, `kmrs.exe` runs without a console window and lives in the notification area (system tray):

- Left-click the tray icon, or choose **Open KMReader** from its menu, to open the web UI. The menu also has Open configuration directory, Open logs folder, Start with Windows, and Exit.
- **Start with Windows** is off by default; tick it to launch kmrs at logon.
- The first start opens the web UI in your default browser so you can create the initial admin account.
- A fatal startup error, such as the port already being in use, is shown in a dialog.
- Started from a terminal, kmrs prints its startup output there and then detaches, so closing the terminal does not stop the server.

  </TabItem>
